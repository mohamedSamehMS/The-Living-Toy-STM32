## 1. Overview

The Living Toy is a handheld gaming device that integrates two graduation-project specifications into one product: Project 1 (a remote-controlled smart device with FOTA) and Project 4 (an interactive gaming hub for children). Each project supplied what the other needed — the gaming hub gave the smart device a reason to exist, and the smart device gave the gaming hub the ability to grow after purchase.

**What it does:**

- Plays four games on a color TFT: **Snake**, **Math Quiz**, **Memory Match**, and **Tic-Tac-Toe** — offline against a tuned AI and online against a friend over the internet
- Greets, plays, loses, and says goodbye out loud — a unique looping theme per game, a lobby waltz, shared win/lose stings, all generated by a software synthesizer
- Is controlled by a 21-button infrared remote and 3 physical buttons — one unified input vocabulary. With the remote in a drawer, every menu (including High Scores and Settings) and the whole firmware-update flow stay reachable on the three buttons; the games themselves need the remote's direction keys
- Updates its own firmware over WiFi: the device shows the offer, the user confirms with two deliberate presses, and the firmware downloads, verifies, installs, and restarts — with a four-layer chain making it impossible to install corrupted firmware or brick the device
- Checks for updates only when asked — nothing ever arrives uninvited

**The development record (bench logs):** 6 real over-the-air updates delivered (largest: the complete 56,844-byte RTOS application), three consecutive with zero manual intervention, 4,851 corrupted-frame retries absorbed on a deliberately hostile link with zero wrong bytes ever written to flash.

## 2. Background & Strategy

The project was built in phases, each isolating one risk class:

- **Phase 1–2 (super-loop):** the complete feature set — drivers, games, menus — was built and hardware-validated on a simple cooperative loop. Concurrency bugs were never mixed with feature bugs.
- **Phase 3 (RTOS migration):** the validated system moved into FreeRTOS in stages — first the whole existing system running unchanged inside one kernel task, then input becoming its own task feeding the rest through a queue, then the network task. Not one line of game code was modified at any stage; each stage re-ran the previous full test list on hardware.
- **Final phase:** audio engine, physical buttons, and the full audio bring-up arc.

The revision history recorded in the source tracks the same progression: MCAL foundations (clock tree, GPIO, SysTick) from mid-July 2026, NVIC/EXTI/USART rework through August, timer, IR/NEC, audio, CRC and flash drivers in mid-September, game modules, hub integration and the FreeRTOS migration around 30 September–1 October, and the buzzer teardown fix on 2 October.

FreeRTOS was chosen over a custom kernel (one was built separately as a learning project, deliberately kept out) for maturity, verified FPU context handling, and out-of-the-box IPC — the deliverable demonstrates system integration, not kernel debugging.

Conscious scope cuts (each recorded with rationale): the LED matrix (TIM4 released back to the free pool), the Music Maker game, and rematch flows. Every shipped piece is load-bearing; the growth path is software delivered over the air, not bolted-on hardware.

### 3.3 The dual-processor topology

*(Diagram: [`Docs/images/architecture-diagram.svg`](Docs/images/architecture-diagram.svg))*

```text
┌──────────────────┐  3-wire UART, 115,200 baud  ┌─────────────┐   WiFi / TLS WebSocket   ┌──────────────────┐
│    STM32F401     │ ◄─────────────────────────► │   ESP8266   │ ◄──────────────────────► │  Python cloud    │
│  FreeRTOS game   │      133-byte frames        │   relay     │                          │  referee + FOTA  │
│  engine          │      (1 seq + 128 + 4 CRC)  │ text ⇄ JSON │                          │  server          │
└──────────────────┘                             └─────────────┘                          └──────────────────┘
```

The design rule: the game engine never touches internet protocols. The ESP owns TLS, WebSockets, and JSON; the STM32 speaks a simple text protocol; the relay translates but never interprets the game. Complexity and attack surface live in exactly one place each. The connection is outbound-only — proven behind a phone hotspot with double NAT, zero router configuration — and carries both game traffic and firmware updates on a single encrypted link.

## 5. Software Architecture — The Four Layers

```text
┌───────────────────────────────────────────────────┐
│  APP  — 4 games · hub & menus · FOTA ceremony ·   │
│         consent flow · online sessions            │
├───────────────────────────────────────────────────┤
│  HAL  — HTFT · HNEC/HIR · HAUDIO · HBUZZER ·      │
│         HESP · HBUTTONS                           │
├───────────────────────────────────────────────────┤
│  MCAL — 10 register-level drivers: GPIO · EXTI ·  │
│         NVIC · RCC · SPI · USART · SysTick(shim) ·│
│         TIM · MFLS(Flash) · MCRC(CRC)             │
├───────────────────────────────────────────────────┤
│  FreeRTOS V11.1 — 4 tasks · queues · tick 1 kHz   │
├───────────────────────────────────────────────────┤
│  Cortex-M4 hardware                               │
└───────────────────────────────────────────────────┘
```

No vendor HAL/LL code is called anywhere in the drivers or the application — every driver is written from the chip's reference manual (RM0368) and ARM's architecture manual (PM0214). The only vendor material in the tree is ST's template startup/CMSIS support under `system/`; the Eclipse template also lists a few ST HAL sources in the build, but nothing references them and the linker discards them (`--gc-sections`).

### 5.1 The Driver Constitution

Every MCAL driver obeys a written rule set, each rule born from a real bug:

- **Validate first, write last** — no function partially applies config; parameters validated before any register is touched.
- **Every function reports success or failure** — never fails silently, no magic sentinels.
- **Hardware facts pinned with compile-time asserts** — a wrong constant stops the build instead of misbehaving at runtime (applied in MRCC, MNVIC, MUSART, MSYSTICK, MFLS, MGPIO, MTIM and MEXTI).
- **NULL means unregister** — callback APIs never crash on unassigned callbacks.
- **One owner per register** — e.g., only MNVIC writes NVIC/AIRCR; SysTick's SHPR3 is a documented exception.
- **Storm-safety** — interrupt sources the driver cannot service can never be enabled (refused with an error).
- **Build-time config validation** — invalid `#define` combinations trigger `#error`.

### 5.2 The ten MCAL drivers

| Driver | Role | Project use |
|---|---|---|
| MRCC | Clock tree + published clock model (all constants derive: baud, timers, SPI) | 16 MHz HSI is active; an 84 MHz PLL_HSE option (M=25, N=336, P=4) is implemented but not enabled. The "silently ignored settings" bug led to build-time config validation |
| MGPIO | Pin control — atomic BSRR writes (no read-modify-write races); package masks protect SWD | Everything on pins; the audio ISR uses precomputed BSRR addresses directly |
| MNVIC | Interrupt controller — vector positions static-asserted to startup file; priorities are the application's job | Vector table remap to 0x08004000 (bootloader); timer IRQ priorities |
| MEXTI | External interrupts — validated tables, sibling-safe atomic W1C on shared vectors | Dormant in the RTOS tree (IR moved to capture; buttons poll) |
| MSPI | SPI, 8/16-bit modes | The TFT on SPI1 @ 8 MHz |
| MUSART | Table-driven UART, integer baud math, storm guards | USART1 (ESP link, frame-based, idle-line detection) + USART2 (console) |
| MSYSTICK | Now the shim — same API over the kernel tick | The whole OS-migration timekeeping story (§8.2) |
| MTIM | General timers — periodic / input-capture / PWM / trigger | TIM5 IR timestamps · TIM10 buzzer · TIM9 audio 16 kHz |
| MFLS | Internal flash read/erase/program — build-time write window (sector 5 only) makes self/bootloader erase impossible | FOTA staging writes; the T1–T6 bench test suite is kept as a scratch harness, not in the shipped image |
| MCRC | Hardware CRC-32 (poly 0x04C11DB7) with a known-answer self-test (`MCRC_SelfTest`, bench-derived constant 0xAE24E09D — differs from the textbook byte-wise CRC-32/MPEG-2 value 0x0376E6E7) | FOTA checksums — verified at three independent points (per frame, whole staged image, trailer) |

### 5.3 The HAL layer

| Driver | Role |
|---|---|
| HTFT | 15 drawing/fill primitives, bufferless direct-pixel rendering (a frame buffer would cost 40 KB of 64 KB); a full-screen fill takes ~26 ms at 8 MHz |
| HIR / HNEC_REMOTE | Two-layer IR: physical pulse timing (calibrated on hardware, two-LED harness) separated from button semantics/repeat policy; 21/21 keys verified |
| HBUZZER | TIM10 hardware PWM tones with three priority levels (input blip < FOTA tones < reserved-high); a timed tone ends through a TIM10 update-interrupt countdown that zeroes the duty cycle before the timer is torn down (the Rev 1 "output frozen high" bug) |
| HAUDIO | The sampled music engine (§9) |
| HESP | ESP link — byte-assembly ring buffer, idle-line frame detection; translates, never interprets |
| HBUTTONS | 3 buttons — polled by the input task every 10 ms, 3-sample debounce, one press = one event |

A shared `HVirtualButtons_interface.h` defines the single `VirtualButton_t` vocabulary that both the remote and the buttons translate into.

## 6. FreeRTOS Usage

### 6.1 The four tasks

| Task | Priority | Role |
|---|---|---|
| Input | 3 (256-word stack) | Decodes IR pulses, polls buttons, translates both into one event vocabulary, posts to the queue every 10 ms |
| Hub/App | 2 (1024 words) | The entire application — menus, running game (Run-owns-the-loop), audio pump |
| Network | 1 (512 words) | Owns the UART wire: pumps the ESP link, parses/executes commands, streams FOTA chunks. USART1 is dark at boot — nothing touches it until online play is entered (the deferred-link ruling, enforced by the absence of the code) |
| Idle | 0 (128 words) | The kernel's own (low-power sleep: designed, not enabled) |

### 6.2 Interrupt priority architecture

Lower number = higher urgency (Cortex-M convention). The syscall mask (BASEPRI = 64, logical 4) is the boundary of the kernel's deal with every ISR:

| Priority | Who | Masked by kernel sections? | May call the kernel? |
|---|---|---|---|
| 0 | SVC (scheduler start); any peripheral IRQ left at its default — EXTI and DMA are unused | Never | NEVER |
| 4 | the syscall mask itself | — | — |
| 5 | TIM5 (IR capture) · TIM9 (audio) · TIM10 (buzzer) · USART1 (ESP link) | Yes | Allowed — FromISR APIs only |
| 15 | SysTick · PendSV (the kernel) | Yes | is the kernel |

The only kernel call made from interrupt context in this build is the tick read in the USART1 RX callback, routed through the IPSR-aware time shim (§8.2).

### 6.3 Memory

`heap_4`, 16 KB — all kernel allocations (task stacks, TCBs, queues). Hub stack 1024 words (4 KB), Network 512 words (2 KB), Input 256 words.

The newlib fence: `_sbrk` is overridden to bound the C library's heap at the linker-defined limit (it returns `ENOMEM` beyond it), and application code never calls `malloc`/`printf` — every allocation goes through FreeRTOS `heap_4`, and the health line is formatted by hand.

Instrumented permanently: the `[ST2]` health line prints every 30 s: `hwHUB`, `hwIN`, `hwNET` stack watermarks (words free), `hp` free heap and `qdrop` input-queue drop counter. Observed in bench sessions: hwHUB≈925/1024, hwIN≈220, hwNET≈320–430, hp≈6,600, qdrop = 0 every time.

### 6.4 Kernel hooks & crash instruments

All four fatal paths — `configASSERT` → `vAssertCalled`, `vApplicationMallocFailedHook`, `vApplicationStackOverflowHook` (stack-check mode 2) and the HardFault handler — drive the failure LED (PA1) solid high and halt. They deliberately do not print: an assert can fire inside an ISR or critical section, where a blocking UART write could itself hang. Boot-time init failures use a separate PA1 blink loop, and the `[ST2]` line above gives the pre-failure picture of stacks and heap.

### 6.5 Configuration highlights (FreeRTOSConfig.h)

- `configTICK_RATE_HZ 1000` guarded by `#error` — the time shim is 1:1 milliseconds only at 1 kHz; a wrong rate stops the build
- `configCPU_CLOCK_HZ` derived from MRCC's published model — the 84 MHz flip recomputes the tick at compile time
- Kernel exception wiring renames (`vPortSVCHandler` → `SVC_Handler` etc.) include a forgetting-detector: re-including the old SysTick driver causes a loud link error
- Unused kernel features are switched off in config (software timers, mutexes and counting semaphores are disabled; `timers.c` is built but contributes nothing) — smallest auditable surface

## 7. Application Architecture

### 7.1 The hub

- **"Menus-as-Data"** — every screen is a static descriptor; one menu engine renders them all
- **"Run-owns-the-loop"** — the hub calls a game's `Run()` and suspends; the game owns control until it returns a result as data; the hub never keeps state inside a game
- **The dispatch table** — row order is an ABI: menu row = game index = high-score slot; the UPDATE row rides the dispatch but takes no score slot (updates aren't a game)
- **Navigation convention:** on the remote, 2/8/4/6 step (CH−/CH+/PREV/NEXT also work), CH selects, 0 goes back; on the buttons, NEXT steps down (wrapping), CONFIRM selects, BACK goes back. Home menu rows: Snake, Tic-Tac-Toe, Math Quiz, Memory, High Scores, Settings, Update.

### 7.2 The input seam

Both input sources are translated into the same `Button_t` event codes through one layer — which is why physical buttons were added in the project's final month with zero changes to any game. Input flows through a kernel event queue: producers post every 10 ms; consumers block on receive (2 ms timeout) — an idle game costs nothing, an arriving event wakes it instantly, and presses made during a ~45 ms repaint wait in memory instead of vanishing.

### 7.3 The games

| Game | Engineering inside |
|---|---|
| Snake | O(1) ring buffer (270 segments), 2-deep direction queue (no double-turn suicide), three levels set in Settings — EASY 320→200 ms with wrap-around walls, NORMAL 250→140 ms, HARD 250→90 ms (4 ms faster per food) — 3-phase death animation, crash sting |
| Math Quiz | Generated questions — division built backwards (divisor and quotient 2–9) so answers are always integers; 3-step error pedagogy (shake → reveal correct → pause); 10 questions per round, 3 hearts, streak bonus capped at 4 points |
| Memory Match | 4×4 grid, 8 glyph pairs, Fisher–Yates shuffle from a seeded LCG, mismatches held face-up 800 ms then input gated a further 300 ms, completion sting |
| Tic-Tac-Toe | Offline AI that plays a rules move (win, block, center, corner) 40% of the time and a random empty cell otherwise, after an 800 ms "think" pause — beatable but competent — plus full online play from the menu; win/lose stings |

## 8. The Three OS Stories (the migration's soul)

### 8.1 The SysTick ownership conflict

Before the OS, one timer was the entire system's sense of time — every deadline consumed one function, `GetElapsed_ms()`. FreeRTOS claims SysTick at scheduler start. One timer, two owners. The fix: a shim — the old driver excluded from the build, the same function name now returns the kernel tick count. Same 1 kHz, same semantics — zero game-code changes; timekeeping survived the OS migration by design, not rewrite.

### 8.2 The interrupt-context crash

The first online session froze completely — deterministic online, never offline, console dead at death. Root cause: the shim returned the kernel's task-context-only tick API, but the WiFi receive interrupt timestamps every incoming byte — an illegal kernel call from ISR context, trapped by the kernel's own assert. The task running at the moment of death was innocent; the culprit was an interrupt that only fired when the ESP spoke. The fix: a context-aware wrapper — reads IPSR (hardware's answer to "am I in an interrupt right now?"), routes each caller to its legal kernel API. One function, every current and future ISR caller, zero call-site changes. The lesson became project law: an API translation layer must audit context-of-call, not just type-of-return — and it later drove the buttons' poll-based design.

### 8.3 The staged migration

Whole system in one task → input task + queue → network task → FOTA wiring — each stage re-running the full hardware test list, not one line of game code modified.

## 9. The Audio Engine

A complete software synthesizer: TIM9 interrupts at 16 kHz (62.5 µs); each interrupt advances a 32-bit phase accumulator (pitch = one number: freq × 2³² ÷ 16,000), looks up one byte of a 256-entry sine table (generated at boot: Q16 fixed-point Taylor through x⁷, quadrant-mirrored so no libm is linked), applies a short envelope (8-sample ramps — nothing ever clicks), and shifts the sample through a 74HC595 into an 8-bit R-2R ladder — 26 direct register stores per sample; the ISR budget comment in the source puts this at ~110 cycles ≈ 11% CPU.

Two-block architecture: the ISR synthesizes autonomously (call-free by law — note advancement needs 64-bit division, a library call); a cooperative pump (`HAUDIO_voidTask()`, called from whatever loop is running) advances songs — const note tables in flash, zero RAM. Stings preempt themes in 0.5 ms (8-sample fade); themes resume when the running loop sees the engine go idle and re-requests them. Each game has its own looping theme and stings (Snake crash, Tic-Tac-Toe win/lose, Math Quiz lose, Memory Match completion), the lobby has a waltz, and welcome/game-over stings frame a session — a consistent emotional vocabulary.

**The bring-up chronicle** (the project's hardest arc): a starvation bug fixed with direct BSRR stores (the original ISR cost 85–95% CPU); a GPIO-port contention bug that silently killed IR input — found by four controlled reflashes bisecting the ISR to pure pin traffic, fixed by moving three wires to PORTA; a stop-machinery deadlock (stale stop request killing a newborn timer — fixed by making the pump the sole timer authority); and a queue-never-armed bug exposed only when the looping lobby theme arrived. Every one closed on the bench.

## 10. Networking

- **Link:** 3-wire UART at 115,200 baud. Game traffic is line-oriented text (`EVENT_` / `CMD_` / `RESP_` names, optional transaction id, CRLF-terminated, 192-byte line buffer); FOTA uses separate 133-byte binary frames = 1 sequence + 128 data + 4 CRC-32, with per-frame ACK (0x06), NAK (0x15) and a 0xAA resync marker; ~15–17 ms per frame (bench)
- **ESP relay (its own firmware project):** TLS-encrypted WebSocket; frame assembly via ring buffer + idle-line detection; auto-reconnect (health every 10 s, rebuild after 35 s); survived outages in bench tests (20.6 s network, 13-min tunnel — no crash, flat memory)
- **Cloud referee (Python):** validates move legality (the toy never trusts the opponent — both ends verified identical, move by move); rooms with 4-letter codes (5-min expiry, 60-second disconnect grace restoring the exact board); serves the FOTA manifest and stream
- **Online latency:** 1.1–1.7 s typical command round trip (10.2 s worst observed); ESP boot-to-connected ~9 s typical (23.7 s worst); 20 s command timeout; 30 s link wait before online play gives up
- **Online Tic-Tac-Toe session:** host / join / rejoin lobby, 4-character room codes typed on a 6×6 on-screen keyboard, host-wait polling every 10 s, a 2 s state poll during the disconnect grace window, and the reconnect credential kept at a fixed SRAM address (`0x2000F000`) so a rejoin can resume the room (reset survival of that address is not hardware-verified)

## 11. Firmware Over-The-Air (FOTA)

### 11.1 Flash memory map (256 KB)

| Region | Size | Contents |
|---|---|---|
| Bootloader | 16 KB (sector 0) | Separate project, not in this repo — has installed 8+ images without ever being reflashed; commits the staged image after reset |
| Application | 112 KB (sectors 1–4, from `0x08004000`) | The running image (~60 KB = 52%) |
| Staging | 128 KB (sector 5) | Where updates land before commit — the only region this firmware can erase or program |

### 11.2 The four-layer verification pipeline

```text
[133-B frame: seq + 128 B + CRC-32] → L1: per-frame CRC + sequence check → [write to staging]
   → L2: end-to-end CRC over the staged image → L3: trailer (own CRC), magic word written LAST
   → L4: bootloader gates on reset (separate project) → new firmware boots
```

- **Per-frame CRC-32 + sequence** — the CRC covers sequence and payload (hardware CRC unit); a bad frame is NAKed and the sender resyncs, a repeated frame (lost ACK) is re-ACKed without writing again
- **End-to-end CRC** — after the last frame, the padded image is read back from staging and checked against the CRC the sender announced
- **Trailer with its own CRC** — a 32-byte trailer (magic `0x464F5441`, firmware version, image length, E2E CRC, trailer CRC) is written first and its magic word last, so the magic is the commit marker: power loss at any instant leaves either the old image or a complete new one
- **Bootloader gates** — header/address validity, independently re-verified from scratch; wrong files declined and wiped (bootloader project)

The receiver evolved through v1.5/v1.6 (proven staging and trailer), v1.7 (sequence byte, duplicate re-ACK), v2.0 (transport-agnostic refactor) and v2.3 (resync validation, see §12).

### 11.3 The consent ceremony

The device checks for updates only when the user opens the UPDATE menu — zero background downloads. The offer shows version and size; two deliberate presses (CONFIRM, then CONFIRM again within 5 seconds) begin the ceremony: progress bar, "DO NOT POWER OFF," automated restart. An accidental bump can never update a child's toy. Numeric version comparison prevents reinstall loops; a 90-second watchdog ends dead sessions cleanly.

### 11.4 The record

6 real OTA WiFi updates · largest 56,844 B (the full RTOS application) · ceremony < 30 s · 3 consecutive zero-intervention runs · cleanest transfer: 113 frames / 7.0 s / zero retries · hostile link test: 4,851 corrupted retries absorbed, 0 wrong bytes ever written.

*These figures come from bench logs and can't be reproduced from the source tree alone. Flash erase timing recorded in the source comments comes from bench runs too (128 KB in 2.33 s, 64 KB in 0.65 s).*

## 12. The Debugging Chronicle

| Bug | Symptom | Method | Fix |
|---|---|---|---|
| One-byte sequence bug | First WiFi transfer stalled; perfect data, silence | Byte-level tap on the wire | Sender counted from 1, spec says 0 — one line |
| Hostile cable noise | 1 byte in 65 corrupted | Protocol stress test | Per-chunk CRC + retransmission — 4,851 retries absorbed |
| Interrupt-context crash | Deterministic freeze, only online | Deterministic reproduction (online only) + LED failure signature | IPSR-aware wrapper — the class eliminated |
| GPIO-port contention | IR died silently, only during music | Four controlled reflashes (binary search) | Three wires moved to PORTA |
| SysTick conflict | One timer, two owners | Architecture review | The shim — zero game-code changes |
| Audio starvation | Boot freeze — ISR ate the CPU | Budget arithmetic at 16 MHz | Direct BSRR stores: ~110 cycles/sample |
| Stop deadlock | Audio died after ~3 play cycles | Paper trace of state machine | Pump = sole timer authority |
| Queue-never-armed | Stings swallowed behind looping theme | Ear + instrument timing audit | Preemption restored with race-fix rails |

The standing lesson, earned three times: structural audits prove what code can't do; only the bench proves what the system does. And when instruments contradict observable behavior, trust the behavior — then audit the instrument's timing.

**Fixes recorded in the source's revision history:**

| Component | Problem | Fix |
|---|---|---|
| MUSART (Rev 1→4) | One-shot RX could not keep up at 115,200 baud; unserviced interrupt sources (IDLE especially) caused IRQ storms | Continuous RX with IDLE framing, unserviceable sources refused, atomic RXNE/IDLE detection |
| HBUZZER (Rev 1→2) | Timer teardown froze the PWM output high, leaving DC on the transducer | Preload CCR to zero one period before teardown so the silent level is latched |
| HIR | 68 ms busy-spin decode plus a ~200 ms swallow window stalled the loop | TIM5 both-edge capture: ~0.2 ms of ISR work per frame |
| FOTA v1.7 | A lost ACK made the sender repeat a frame the receiver had already written | Previous sequence is re-ACKed without a second write |
| FOTA v2.3 | `0xAA` can occur inside payload; marker-only resync locked into a repeating "frame-7 attractor" | The byte after the marker must match the expected or previous sequence before collection resumes |
| Tic-Tac-Toe F-R1 / F-R2 | Exit-resume polarity inverted; moves arriving during the exit prompt were dropped | Correct ON_TURN / ON_WAIT resume plus a state request to resynchronize |
| Tic-Tac-Toe M7 / A1 | Missing parentheses let a stale button be read on no-event passes | Button interpreted only when an IR event is present |

*(`Docs/` also holds the architecture/code-review audit trail generated during development.)*

## 14. Building & Flashing

1. Import into Eclipse CDT (`File → Import → Existing Projects into Workspace`; `.project` and `.cproject` are committed) and build — Eclipse regenerates the managed makefiles under `Debug/`, which is git-ignored.
2. Compiler: `arm-none-eabi-gcc`, flags per §4 (`-std=gnu11 -Wall -Wextra`); link with `-T mem.ld -T libs.ld -T sections.ld --gc-sections --specs=nano.specs` — FLASH starts at `0x08004000` (112 KB), RAM is 64 KB.
3. Output: `.elf` → `.hex` (objcopy). Size: text 59,359 + data 780 = 60,139 B flash; bss 22,364 B RAM.
4. Flash via SWD. Console: PuTTY on the USART2 port, 115,200 baud.
5. Boot verification: the banner, then `[ST2]` health lines every 30 s.

The firmware version lives in `APP_BUILD_VERSION_STR` (`main.c`) and `NET_FW_ID` (`NET_config.h`); release builds carry 14.4.0. With `APP_FOTA_NET_VERSION_POLICY = 1` the toy only accepts strictly newer images, so FOTA test images are built with a lower number.

## 15. User Manual

### 15.1 Getting started

Power on. The toy greets you with a short welcome sound, then the lobby menu appears with quiet background music. A small LED on the board blinks steadily in the menus, Tic-Tac-Toe and the update screen — that's the heartbeat, proving the system is alive.

### 15.2 Controls — two ways, one behavior

**The remote (primary):** number keys 2 / 8 / 4 / 6 move the selection up/down/left/right (CH−, CH+, PREV and NEXT work too), CH confirms, 0 goes back. Direction keys repeat when held — menus glide.

**The three buttons (fallback):** CONFIRM selects, BACK exits, NEXT steps down through the list (wrapping around). With the remote's batteries dead, you can still reach every menu, High Scores and Settings, and run a firmware update — but the games need the remote's direction keys.

Every press on either input gets a short confirmation beep.

### 15.3 The games

**SNAKE** — guide the snake to the food; it grows and speeds up. Easy mode wraps the walls; Normal and Hard walls end the run. The high score is remembered until the toy is powered off, and the difficulty (Easy / Normal / Hard) is chosen in Settings. When you crash, you'll hear the losing sting.

**MATH QUIZ** — ten questions per round with three hearts. Wrong answers don't just say "wrong": the screen shakes, the correct answer is shown, then a short pause — see it, learn it, continue. Streaks earn bonuses.

**MEMORY MATCH** — a 4×4 grid of face-down cards; flip two at a time and find all eight pairs. Mismatches stay visible briefly — memorize, then try again. Completing the grid plays the victory sting.

**TIC-TAC-TOE** — two ways to play:
- *Offline:* against the toy's built-in opponent. It's tuned so a child wins more often than not — but not always.
- *Online:* choose to create a room — a 4-letter code appears on your screen — and a friend joins by typing that code on their toy. Moves travel over the internet in one to two seconds. If the connection drops, the room is held for 60 seconds and the board restores exactly on reconnect.

**UPDATE** — the firmware update row (see below).

### 15.4 Updating the toy

The toy checks for new software only when you open the UPDATE row — nothing ever downloads in the background.

1. Open UPDATE from the menu. If new firmware exists, the toy shows its version and size.
2. Press CONFIRM, then CONFIRM again within 5 seconds — two deliberate presses, so nothing starts by accident.
3. The toy takes over: a progress bar fills while firmware downloads and verifies. Do not power off during this time (the toy tells you).
4. The toy restarts itself running the new version — announced on the banner.

If no update is available, or the connection is down, the toy says so and you simply back out. The update itself is protected at every step: corrupted data is detected and re-downloaded, and even a power cut mid-update can never leave the toy broken.

### 15.5 Troubleshooting

| Symptom | What it means / what to do |
|---|---|
| Remote not responding | Batteries dead or remote pointed away — the three buttons still reach every menu and the update flow, but the games need the remote's direction keys |
| No sound in the earpiece | Check the earphone jack connection; the button beeps come from the separate buzzer, so beeps + silence in the ear = check the jack |
| Online game: "no connection" | The WiFi network is unreachable — try again near the router; offline play is unaffected |
| Update fails | The toy keeps running its current firmware untouched — simply try again later |
| Fault LED (PA1) solid | The kernel caught a fatal fault (assert, allocation failure, stack overflow or HardFault) — power-cycle; blinking at boot means a boot-time init step failed. Watch the console `[ST2]` line for stack/heap trends |

## Known Limitations

- High scores and the Snake difficulty live in RAM and reset at power-off (no flash persistence in this build)
- The games need the remote's direction keys; the three buttons cover menus, settings, high scores and the update flow
- The PC13 heartbeat only runs in the menus, Tic-Tac-Toe and UPDATE (not during Snake, Math Quiz or Memory Match)
- Fatal faults light PA1 solid and halt — there is no persisted crash log
- `MCRC_SelfTest` and the MFLS T1–T6 suite are bench tools, not run at boot in the shipped image
- Online play needs a reachable backend referee (a laptop behind a Cloudflare Quick Tunnel whose URL changes on each restart)
- Reconnect credentials sit at a fixed SRAM address (`0x2000F000`); surviving a reset there is not hardware-verified
